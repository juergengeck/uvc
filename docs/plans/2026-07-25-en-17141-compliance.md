# EN 17141 compliance evidence implementation plan

## Outcome

Implement
[`one/EN17141.book/EN17141-PRD.md`](../../one/EN17141.book/EN17141-PRD.md)
as two connected domains:

- `@refinio/biocontamination.core` owns the reusable EN 17141 quality model;
- `@refinio/uvc.core` owns UV-C intervention authorization, execution,
  physical-delivery evidence, and the adapter into that quality model.

Existing `UvcDisinfectionRun` objects remain device-cycle records. They are not
migrated, reclassified, or treated as proof of physical delivery,
microbiological effectiveness, or EN 17141 conformity.

The authored `one/EN17141.book` folder is the authoritative Book source.
This plan is a UVC implementation plan that consumes that source; it is not part
of the Book boundary. VGER inventories the tracked documents at a Git checkpoint
and records their `Source`, `SourceEntry`, `SourceRun`, `BookProjection`, `Book`,
and `Library` lineage.

Delivery is split into vertical slices. Every slice includes its recipes,
creator validation, storage, trie placement, CHUM closure, plan logic,
operations, projections, and tests before the next slice starts. The product
must continue to run between slices, but no conformity claim is enabled by an
incomplete slice.

The governing semantic boundary is:

```text
device command/readback
        ↓
UVC cycle execution
        ↓
calibrated physical-delivery assessment
        ↓
separate microbiological observations and assessment
        ↓
qualified facility review and program decisions
```

No arrow may be skipped and no downstream meaning may be inferred from an
upstream record.

## Implementation clarifications

### Ownership invariant

Inventory, supply, laboratory, device, and facility systems may produce facts
referenced by the quality graph. They do not own applicability, monitoring
plans, limits, result interpretation, excursions, CAPA, or qualified closure.

Generic quality types use the `Biocontamination` prefix and live in
`@refinio/biocontamination.core`. Only UV-C-specific types use the `Uvc` prefix
and live in `@refinio/uvc.core`. Cross-domain relationships are typed
`referenceToId` or exact `referenceToObj` fields; neither package duplicates
the other's evidence.

Two contracts are required in addition to the objects already named in
[`one/EN17141.book/EN17141-PRD.md`](../../one/EN17141.book/EN17141-PRD.md).

### Local program-root registry

Add a versioned `BiocontaminationProgramRegistry` with identity
`ownerPersonId + ownerInstanceId`. It is a local index of known program ids and
their deterministic `BiocontaminationTrieRoot` id hashes.

- Fields are `$type$`, `$version$: 'v1'`, `ownerPersonId`,
  `ownerInstanceId`, `knownProgramRoots:
  Set<SHA256IdHash<BiocontaminationTrieRoot>>`, `createdAt`, and `updatedAt`.
- Update it when a local program is created or a shared program root is
  accepted.
- Do not share the registry through IdAccess.
- Do not put compliance evidence in it.
- Do not include it in `BiocontaminationEntry`, trie allowed types, or CHUM sync
  types; it is local runtime infrastructure.
- Use it to reopen known program roots after restart without scanning ONE
  storage or probing object types.
- Keep the program-scoped biocontamination trie as the only shared quality
  evidence root.

### Controlled execution operations

Add `startIntervention` and `terminateIntervention` to the canonical
`uvc-intervention` operation. `planIntervention` alone cannot enforce
authorization if treatment is still started through generic device-control
methods.

Add immutable `UvcInterventionAuthorizationAttempt` evidence for both accepted
and rejected attempts. A rejected attempt records the exact plan version,
actor, evaluated preconditions, outcome, and time without energizing hardware.
The object contains the program, caller-supplied request id, exact intervention
plan hash, actor Person/Instance, exact actor qualification, exact evaluated
evidence refs, decision, reason codes, and evaluation time.

Generic `deviceControl` operations may remain available for diagnostics, but
the UI and integrations must not present them as a controlled treatment or
compliance workflow.

### refinio.api boundary

`BiocontaminationPlan` remains the quality-domain plan.

- demand exact existing runtime dependencies through `ModuleRegistry`;
- initialize one `BiocontaminationPlan`;

- `OperationRegistry`: already supplied by `ModuleRegistry`.

private keys or let callers substitute producer identity on a write.

`UvcInterventionModule` separately demands:

- `BiocontaminationPlan`, required;
- `UvcFacilityPlan`, required;
- `UvcControlPlan`, required;
- the UVC runtime's identity, storage, signing, and clock supplies;

### Expo and Cube

1. the complete recipe and reverse-map configuration is installed;

4. `BiocontaminationPlan` is supplied;

Browser/shared UI consumes typed operations and projections only. Groov and
ESP32 continue to own device observations and may produce approved safety or
dose observations only when the corresponding sensor, calibration, and
procedure contracts are implemented.

## Core storage contracts

### Stored facility transitions

Introduce:

```ts
interface StoredUvcDisinfectionRun {
  run: UvcDisinfectionRun;
  hash: SHA256Hash<UvcDisinfectionRun>;
  idHash: SHA256IdHash<UvcDisinfectionRun>;
}
```

Change `scheduleDisinfection`, `startDisinfection`,
`completeDisinfection`, and `failDisinfection` to return this result.
`UvcFacilityPlan.storeAndAppend` returns the exact values produced by
`storeVersionedObject`.

Migrate current Expo and Cube callers in the same change:

- domain callers consume all three fields;
- UI adapters project `stored.run`;
- tests assert that the returned `hash` is the hash appended to the journal;
- no caller recalculates a hash or asks for the latest version to bind
  terminal evidence.

Because `@refinio/uvc.core` is pre-1.0 and all current callers are in the
workspace, prefer one explicit contract migration over parallel legacy
methods.

### Biocontamination storage

`BiocontaminationStorage` exposes typed operations, not generic JSON:

- store/load versioned compliance objects;
- store/load immutable compliance evidence;
- calculate id hashes from declared id objects;
- load an exact object hash;
- load a current version only when creating a new prospective workflow;
- append the storage-returned hash to the owning program trie;
- load entries from explicit trie paths.

Every write helper returns the exact stored hash and, for versioned objects,
the id hash. Creator validation runs before storage. The storage adapter never
adds defaults for missing required facts.

### Program trie

Add:

```text
biocontamination:<ownerPerson>:<ownerInstance>:<programId>:v1
```

through `makeBiocontaminationTrieRootId`. Use the package-owned
`BiocontaminationTrieRoot` and its root-only `shareWith` behavior.

Extend:

- the package-owned `BiocontaminationEntry` union;
- `getBiocontaminationStatePaths` with quality paths;
- the package-owned persisted trie allowed-type set;
- `BIOCONTAMINATION_STATE_SYNC_TYPES` and
  `BIOCONTAMINATION_CHUM_SYNC_TYPES`;
- the CHUM closure allowlist with referenced non-entry types such as
  `Signature`, `Person`, `Instance`, and version-graph nodes;
- recipe closure tests for all exact refs.

Minimum canonical paths are:

```text
program
environment/<environment-id-hash>
type/<object-type>
status/<workflow-status>
effective/<object-family>
intervention/<intervention-id>
request/<request-id>
sample/<sample-id>
excursion/<excursion-id>
subject/<person-id>
```

Add more paths only for a real query. Do not use reverse-map traversal or
storage scans as a substitute for a missing canonical path.

## Slice 1 — Program authority and evidence root

### Objects

Implement:

- `BiocontaminationProgramReviewState`
- `BiocontaminationProgram`
- `BiocontaminationProgramRegistry`
- `BiocontaminationControlledEnvironment`
- `BiocontaminationControlledDocumentRevision`
- `BiocontaminationControlStrategy`
- `BiocontaminationResponsibilityAssignment`
- `BiocontaminationPersonnelQualification`
- `BiocontaminationApproval`
- `BiocontaminationApplicabilityDeclaration`

For every versioned object, define an explicit compact id-object interface.
For every immutable object, use content addressing directly. Add `$version$:
'v1'` exactly as required by the PRD.

### Logic

- Create/update program and environment authority.
- Store exact controlled-document revisions.
- Validate qualification scope, effective period, expiry, suspension, and
  producer identity.
- Approve or reject an exact version hash with an injected signer.
- Verify the signature and the exact qualification revision at decision time.
- Resolve applicability by standard edition and activity time.
- Reject missing, expired, overlapping, contradictory, or unapproved
  applicability.
- Build `getEvidenceTrace` by walking declared forward refs from a requested
  conclusion; return hashes, id hashes, recipe versions, signatures,
  limitations, and missing refs.
- Project `getProgramStatus` as independent dimensions. Do not add one
  `compliant` boolean.

### Runtime integration

- Initialize the local program registry and deterministic program tries.
- Initialize `BiocontaminationModule` in Expo and Cube.
- Register the first authority operations under `biocontamination`.
- Export quality reverse-map declarations from `biocontamination.core`, even
  when a family intentionally needs no reverse map. Compose them with
  `ReverseMapsStable`, `ReverseMapsExperimental`, existing app maps, and their
  id-object counterparts in each `MultiUser` constructor; a custom map must
  not replace the defaults.
- Share only a selected program trie root.
- Route imported compliance roots to `BiocontaminationPlan.consume`.
- Persist known imported program roots in the local registry without copying
  their evidence.
- Emit one plan update only when imported semantic state changes.

### Gate

- A program can make an approved applicable, partially applicable, or
  not-applicable declaration.
- Applicability is never inferred from `roomKind`.
- Editing an approved object creates an unapproved version.
- Restart reopens known program roots through the local registry with no
  storage scan.
- Repeated CHUM import creates no duplicate evidence.
- Root sharing creates no per-entry or per-child grants.

## Slice 2 — Risk, monitoring, methods, equipment, and limits

### Objects

Implement:

- `BiocontaminationSourceRoute`
- `BiocontaminationMicroorganismOfInterest`
- `BiocontaminationRiskHazard`
- `BiocontaminationRiskMitigation`
- `BiocontaminationResidualRisk`
- `BiocontaminationRiskAssessment`
- `BiocontaminationMonitoringLocation`
- `BiocontaminationSamplingSchedule`
- `BiocontaminationSamplingMethodRevision`
- `BiocontaminationEquipmentQualification`
- `BiocontaminationCalibrationRecord`
- `BiocontaminationEquipmentVerification`
- `BiocontaminationLimit`
- `BiocontaminationLimitSet`
- `BiocontaminationMonitoringPlan`
- `BiocontaminationChangeControl`

### Logic

- Reject an approvable risk assessment without hazards, mitigations, residual
  risk conclusions, or scientific rationale.
- Require exact risk-assessment versions on locations and monitoring plans.
- Require monitoring plans to bind exact location, method, limit-set, schedule,
  and excursion-procedure revisions.
- Resolve effective versions at the prospective activity time and write those
  exact hashes into the new sample/intervention context.
- Validate non-overlapping effective periods where only one revision is
  allowed.
- Model measurement units explicitly. Comparisons accept identical units or a
  reviewed, deterministic conversion declared by the method; otherwise they
  fail closed.
- Model equipment status from exact qualification, calibration, and
  verification evidence. “Device online” is not equipment suitability.

### Gate

- Approved risk, monitoring, method, and limit revisions form a complete exact
  graph.
- Historical resolution tests prove later master-data edits do not reinterpret
  earlier contexts.
- Missing or expired qualifications, calibration, methods, or limits produce
  an incomplete decision and block controlled writes.

## Slice 3 — Controlled UVC intervention

### Objects

Implement:

- `BiocontaminationControlMethodRevision`
- `UvcTreatmentConfigurationRevision`
- `UvcDoseSpecificationRevision`
- `UvcCoverageVerificationRevision`
- `UvcSafetyConditionDefinition`
- `UvcTreatmentProcedure`
- `UvcInterventionPlan`
- `UvcInterventionAuthorizationAttempt`
- `UvcSafetyObservation`
- `UvcDoseObservation`
- `UvcInterventionDeviation`
- `UvcInterventionExecution`
- `UvcPhysicalDeliveryAssessment`

### Shared execution coordinator

Move the treatment orchestration currently embedded in Expo
`DeviceControlModel.startRoomTreatment` and `stopRoomTreatment` behind
`UvcInterventionService`:

1. load the exact intervention-plan version;
2. ask `BiocontaminationPlan` to resolve and verify the exact program,
   approvals, effective revisions, qualification, and blocking quality state;
3. verify the exact `UvcRoom` version and resource configuration;
4. verify the returned operator qualification and equipment evidence;
5. verify UVC-specific safety and configuration evidence;
6. store an accepted or rejected authorization attempt;
7. on acceptance only, call `UvcControlPlan`;
8. require a matching start readback for every resource;
9. on partial start, perform the existing verified rollback and record
   failure/deviation evidence;
10. monitor procedure-required safety observations;
11. stop through `UvcControlPlan`;
12. require stop readbacks;
13. store the terminal facility transition and retain its storage-returned
    hash;
14. create one immutable execution referencing that exact terminal hash and
    every available observation.

The execution keeps exact `UvcControlObservation` refs; their declared
`UvcControlCommand` refs preserve the commanded-versus-observed chain.

`startIntervention` returns the authorization attempt and running stored run.
`terminateIntervention` returns the exact terminal stored run and immutable
execution. Both operations require a caller-stable request id. Before any
physical write, the plan queries the request-id trie path and returns the
existing outcome when that request was already processed. Attempts and
terminal executions retain that request id, so a retried request cannot create
duplicate physical history.

### Physical assessment

- Use calibrated `UvcDoseObservation` objects only.
- Verify wavelength/spectrum, target location, coverage, units, calibration,
  equipment status, time interval, interruption, and uncertainty.
- Produce `meets-approved-criteria`,
  `deviates-from-approved-criteria`, or `inconclusive`.
- Keep `UvcDisinfectionRun.uvcDoseMjCm2` display-only unless its value is
  supported by the exact reviewed dose-observation set.

### Gate

- Missing authority, qualification, safety, calibration, or configuration
  prevents hardware energization.
- Partial start rolls back and records attributable evidence.
- A safety violation executes the approved stop path.
- A completed readback sequence produces `cycleState: executed`, not a
  microbiological or conformity conclusion.
- The execution points to the storage-returned terminal run hash.
- Expo and Cube use the same coordinator and decision logic.

## Slice 4 — Microbiological sampling and result evaluation

### Objects

Implement:

- `BiocontaminationSample`
- `BiocontaminationSampleCustodyEvent`
- `BiocontaminationObservation`
- `BiocontaminationResult`
- `BiocontaminationResultEvaluation`
- `BiocontaminationInterventionEffectivenessAssessment`
- `BiocontaminationExcursion`
- `BiocontaminationContainmentAction`

### Logic

- Create a sample only from an approved effective monitoring plan.
- Bind exact plan, risk, location, method, limits, schedule, collector
  qualification, equipment, operating state, and optional intervention
  execution at collection time.
- Append custody events; never update or replace an earlier event.
- Validate custody sequence and expose gaps or condition deviations.
- Reject device telemetry as a microbiological observation or result.
- Preserve raw observation, medium, incubation, analyst, organism, count, and
  interference evidence.
- Evaluate a result against the limit revision stored on its sample.
- Match method, location/scope, operating state, organism scope, measure, and
  unit before comparing a number.
- Deterministically open the required excursion from the result and breached
  limit so evaluation retries are idempotent.
- Keep physical-delivery and microbiological-effectiveness assessments
  independent even when they reference the same intervention.

### Gate

- Samples cannot be created with current master data substituted for missing
  historical context.
- Custody gaps and invalid observations remain visible.
- Alert/action/specification outcomes are reproducible from the exact evidence
  graph.
- Raw device telemetry cannot pass a recipe, creator, or operation boundary as
  viable microbiological evidence.

## Slice 5 — Investigation, CAPA, trending, and periodic review

### Objects

Implement:

- `BiocontaminationInvestigation`
- `BiocontaminationCapa`
- `BiocontaminationCapaAction`
- `BiocontaminationEffectivenessCheck`
- `BiocontaminationTrendReview`
- `BiocontaminationPeriodicReview`

Complete `BiocontaminationChangeControl` workflows introduced in Slice 2.

### Logic

- Enforce explicit excursion state transitions.
- Require attributable containment, investigation, root-cause conclusion,
  CAPA actions, effectiveness checks, and qualified closure as configured by
  the applicable procedure.
- Keep contradictory evidence and rejected hypotheses in the trace.
- Build trend strata only from compatible method, location/scope, operating
  state, unit, limit regime, and organism scope.
- Require an explicit reviewed stratification rule before combining unlike
  series.
- Store exact input result/evaluation hashes, calculation revision, missing
  data, exclusions, reviewer qualification, conclusion, and signature on each
  trend review.
- Build periodic review from exact applicability, risk, monitoring,
  intervention, microbiology, excursion, CAPA, change-control, qualification,
  and trend evidence.
- Export a signed, independently verifiable evidence manifest. Export is a
  projection of stored refs, never a replacement source of truth.

### Gate

- Excursions cannot close without their configured investigation and
  effectiveness evidence.
- Trends cannot silently cross incompatible scopes.
- Periodic review reports limitations and incomplete dimensions.
- No operation or projection emits a single unqualified conformity boolean.

## State-machine rules

Use explicit transitions. Reject all unlisted transitions.

```text
controlled revision: draft → in-review → approved → withdrawn/superseded

intervention:
planned → authorized → running → executed/failed/cancelled
planned → rejected

sample:
created → collected → in-transit → received → processed → reviewed
any pre-review state → deviated/invalidated

excursion:
open → contained → investigating → capa-open → effectiveness-review → closed
```

Approval is immutable evidence about one exact subject hash; it is not a
mutable state field that floats to later versions. Lifecycle status on the
subject is only a projection unless the exact approval also exists and
verifies.

## Public operation contract

Implement the PRD operations plus:

- `shareProgram`
- `revokeProgramShare`

Register quality operations once under `biocontamination`. Register
`planIntervention`, `startIntervention`, `recordSafetyObservation`,
`recordDoseObservation`, `terminateIntervention`, and
`assessPhysicalDelivery` once under `uvc-intervention`.

Each mutation:

1. obtains actor Person/Instance from the injected runtime;
2. validates the typed input;
3. resolves the exact effective context;
4. verifies actor qualification/authority;
5. stores using the correct ONE storage API;
6. appends the returned hash to the program trie;
7. returns exact object/hash/id-hash output;
8. emits one semantic plan update.

Operation inputs never accept producer Person/Instance ids from a renderer or
remote caller.

## Pull-request sequence

Keep changes reviewable in this order:

1. claim-safe vocabulary and exact facility-transition results;
2. compliance folder, core authority recipes, and local program registry;
3. program trie, paths, closure, and CHUM policy;
4. authority plan, evidence trace, module, and operations;
5. Expo/Cube bootstrap, sharing, imports, and authority projections;
6. risk and monitoring schema/effective-revision logic;
7. intervention schema and authorization;
8. shared execution coordinator and physical-delivery assessment;
9. samples, custody, microbiological observations, and results;
10. result evaluation, excursions, and effectiveness assessment;
11. investigation, CAPA, change control, and trending;
12. periodic review, signed export, cross-runtime validation, and operational
    documentation.

Each pull request must include the affected recipe/storage/CHUM tests. Do not
merge a recipe-only change that leaves a runtime with a partial custom recipe
list.

## Release gates

A compliance-capable release is blocked until all of the following are true:

- the licensed standard and facility-specific applicability assessment are
  available to the accountable organization;
- all applicable recipes are registered before reads/writes in every runtime;
- exact storage hashes flow into conclusions without recomputation;
- program sharing uses only stable root IdAccess;
- historical evidence resolves from stored refs rather than current master
  data;
- intervention authorization fails closed before hardware writes;
- device, physical, microbiological, and facility conclusions remain separate;
- OOS/CAPA/trend/review workflows retain exact lineage;
- signed evidence export verifies independently;
- automated, distribution, physical, and laboratory validation appropriate to
  the enabled scope is complete;
- product and operator documentation states limitations and avoids an
  unsupported conformity claim.

The first release may ship Slices 0–2 as an evidence-management preview, but
must label controlled intervention, microbiological, and conformity workflows
unavailable until their corresponding gates pass.
